Now let's step back and compare these two alternatives at a high level. The differences between these two classes fall into two broad categories.

The first category is the feature level support that each of these two classes provides. This slide compares the two types side by side. HTTP client was designed to provide a more modern, efficient, and feature-rich API for HTTP interactions, starting with its support of both HTTP protocols. HTTP client supports both synchronous and asynchronous request and response handling. So far I've only shown you synchronous examples. I'll be showing you asynchronous techniques in the next video.

HTTP client comes with built in support for the response body handling and the request body handling, as you've seen with body handlers and body publishers. In addition, there's also built-in support for features like cookies and redirects. Even more importantly, HTTP client is able to provide support for more advanced features such as specifying compression and authentication schemes. The second category of comparisons between these types, falls into a category I'll call application design support.

This slide compares the two types side by side. HTTP client was designed to address limitations of HTTP URL connection, as well as align with contemporary development practices. You've seen that it uses a builder-based model to construct specific objects like a request. With HTTP URL connection, these were all different method calls on the connection object itself, which didn't differentiate between the connection, the request, or the response. Response handling comes with helper functions as you've seen, but can also be used in reactive programming streams, which I haven't really covered.

Reactive programming is a programming paradigm that focuses on asynchronous data streams and the propagation of changes, and it's becoming increasingly popular. I hope you've also seen how easy it was to use the HTTP client, with its support for the basic tasks, meaning we didn't have to deal with input and output streams and conversions to bytes and back, or with encoding and decoding, which makes using Http URL client very verbose. HTTP client provides a more modern alternative to Http URL connection.

It's an efficient and feature-rich API for HTTP interactions. Oracle has been prioritizing development efforts on HTTP client, indicating a clear preference for its usage in new projects. Leading frameworks and libraries in the Java ecosystem, such as Spring, are increasingly adopting the JDK's HTTP client. HTTP URL connection is still usable, but its future is uncertain. So, you should use Http client for new projects in preference over HTTP URL connection.

It's the preferred choice, due to its modern design, performance, and ease of use. You should consider migrating existing code to HTTP client, for better maintainability and alignment with future java development trends.
