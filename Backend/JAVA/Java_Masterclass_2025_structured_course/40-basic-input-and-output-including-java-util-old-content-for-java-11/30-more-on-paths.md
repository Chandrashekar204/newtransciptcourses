So the java.io file class also points to files on the file system.

So why did the java developers introduce another class that effectively does the same thing in java 7. So the file class more useful though has a few problems. And specifically, those problems are firstly, many methods in that class don't throw exceptions or don't provide specific error messages when they fail. An example would be the file.delete method which returns a boolean. And if the deletion fails, you can't actually tell if it was because the file didn't exist or the application doesn't have permission to delete the file or some other reason.

So unfortunately, the method doesn't provide that level of information. Now the file.rename method works differently on different platforms. And java is supposed to be portable as across platforms meaning that the code shouldn't have to worry about which operating system it's running on. Another problem there's no support for symbolic links. And a symbolic link is a kind of file that points to another file sort of like a shortcut in windows if you're familiar with that.

Now they're often used with networks to point to a remote location. Unfortunately, the file class doesn't understand those symbolic links. The file class doesn't provide a way to get metadata about a file information such as permissions, its owner or other security information. The metadata that it does provide is retrieved inefficiently as well. Now many of the methods don't perform well when working with lots of data. For example, if you use the file class to request a list of all the files in the directory and there are a lot of files the method can actually hang believe it or not.

And lastly, the last error since the file class doesn't understand symbolic links walking through a directory tree is therefore problematic.
