# 12.2 — Details about method invocation authorization in method level security

> Section 12: Method Level Security

Instructor: The very first approach that we can use to implement the method-level security is Invocation authorization. With this approach, we should be able to control whether the method can be invoked or not based upon our authorization rules. So let's try to understand how to implement this Invocation authorization with the help of Spring Security framework. Invocation authorization can be achieved with the help of two important annotations that are available as part of Spring Security framework.

The very first annotation is @PreAuthorize annotation, and the other annotation is @PostAuthorize annotation. So first, let's try to understand what is the purpose of @PreAuthorize annotation. This @PreAuthorize annotation, we should be able to mention these on top of a class or on top of a Java method. The class and Java method, they can be present inside any layer. Regardless of where your Java method and Java class are present, you can happily use this annotation to enforce the authorization rules.

Most of the times, developers, they're going to use this annotation on top of the Java methods. Using them on top of a Java class is very rare scenario. The syntax to use this annotation is first you need to mention @PreAuthorize annotation. To this annotation, we should be able to provide our authorization configurations as an input. Here I have mentioned various flavors. I just mentioned these annotation multiple times on top of my method just to show you the list of common use cases of this annotation.

But in reality, you are not allowed to use this annotation multiple times on top of a method. So to this method, if you pass the hasAuthority, hasRole, hasAnyRole or has any authority methods along with the authority name or role details, behind the scenes, Spring Security framework, it is going to perform the validations, whether a given end user has enough authority or roles to invoke this method. If the end user does not have given role or authorities, then Spring Security, it is going to throw the 403 error.

Here you may have a question, which is, we are already applying the authorization rules on top of our APIs. Then what is the need to apply the same authorization rules on top of a method again? So this can be your question. To answer your question, let's take a real-life example. If you go to any bank, there are multiple layers of security. So just like how bank is trying to have multiple security layers, similarly, for critical web applications, we will have these kind of requirements to enforce authorization rules at multiple layers. When we enforce the authorization rule on top of a API, the Spring Security, it is only going to perform the authorization checks during the API invocation or MVC path invocation. But as part of that API or MVC path, we may invoke 100 different Java methods.

If the hacker is somehow able to invoke the API without any proper role or proper authority, we should also have some extra check by enforcing these authorization rules with the help of these annotation. If someone is trying to manage to invoke this method with a different username, they will not be able to invoke it due to the method-level security that we are trying to enforce here.

So this is one style of enforcing the invocation authorization. The other style, like I was telling, it is with the help of @PostAuthorize annotation. This @PostAuthorize annotation, it is going to work exactly opposite of @PreAuthorize annotation. When we enforce an authorization rule with the help of @PreAuthorize annotation, the Java method is never going to be invoked if the authorization check fails; whereas when we're using the @PostAuthorize annotation, the Spring Security framework is not going to perform any authorization checks during the method invocation.

Once the method invocation is completed and the method execution is completed while returning the output from the method, at that point of time, the Spring Security framework, it is going to enforce the authorization checks that we have mentioned here. You may have a question here, which is, under which scenarios we are going to use @PostAuthorize annotation. This seems to be very odd to me why anyone want to invoke a method without authorization but enforce authorization while returning the output.

This can be your question. Let me try to answer your question. Sometimes during the method invocation, you may not have enough information to enforce the authorization. But once the method execution is completed and once the method is trying to return the object, using the return object, you want to enforce authorization. In such scenarios, we can use the @PostAuthorize annotation. There is no meaning to use @PostAuthorize annotation with the hasAuthority, hasRole, and hasAnyRole approaches, because these approaches we can happily use with the @PreAuthorize annotation.

But technically, it is possible to use these styles with the help of @PostAuthorize annotation. But if you try to look at the last syntax or last two configurations that I have, this is the scenario where it is going to make more sense to use @PostAuthorize annotation. So here I'm trying to enforce the authorization based upon the return object that I'm trying to return here. Inside this return object, if we have a field with the name username, we can compare it with the logged-in user username. So if the logged-in user username is same as with the username present inside the return object, then only we want to return the object. Otherwise, we want to stop returning that object by throwing the 403 error. Many times we have Java methods where they're not going to accept any input parameter, but they're going to return a good amount of objects.

Think, like, I have a method which is getLoans(). And this method is not going to accept anything, but it is going to return list of loans as an output. Here I can't enforce authorization based upon the username using the @PreAuthorize annotation, because this method, it is not accepting any input parameter; Whereas by inspecting the return object, I will be able to apply the authorization checks with the help of @PostAuthorize annotation.
