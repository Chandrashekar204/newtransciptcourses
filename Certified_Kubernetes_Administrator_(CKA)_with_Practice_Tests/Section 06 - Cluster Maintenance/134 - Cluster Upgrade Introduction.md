# Cluster Upgrade Introduction

*Section: Cluster Maintenance*

1 In this lecture, 2 we discuss about cluster upgrade process in Kubernetes. 3 In the previous lecture, 4 we saw how Kubernetes manages its software releases 5 and how different components have their versions. 6 We will keep dependency on external components 7 like etcd and CoreDNS aside for now 8 and focus on the core control plane components. 9 Is it mandatory for all of these to have the same version?

10 No, the components can be at different release versions. 11 Since the kube-apiserver is the primary component 12 in the control plane, 13 and that is the component that all other components talk to, 14 none of the other components should ever be 15 at a version higher than the kube-apiserver. 16 The controller manager and scheduler can be 17 at one version lower. 18 So if kube-apiserver was at X, controller-managers 19 and kube-schedulers can be at X-1.

20 And the kubelet and the kubeproxy components 21 can be at three versions lower, X-3. 22 So if kube-apiserver was at 1.10, 23 the controller-manager and scheduler could be at 1.10 or 1.9 24 and the kubelet and kubeproxy could be at 1.7. 25 None of them could be at a version higher 26 than the kube-apiserver like 1.11. 27 Now this is not the case with kube control. 28 The kube control utility could be at 1.11, 29 a version higher than the API server, 30 1.10 the same version as the API server, 31 or at 1.9 a version lower than the API server.

32 Now this permissible skew in versions allows us 33 to carry out live upgrades. 34 We can upgrade component by component if required. 35 So when should you upgrade? 36 Say you were at 1.10 37 and Kubernetes releases versions 1.11 and 1.12. 38 At any time Kubernetes supports 39 only up to the recent three minor versions. 40 So with 1.12 being the latest release, 41 Kubernetes supports versions 1.12, 1.11, and 1.10.

42 So when 1.13 is released, only versions 1.13, 1.12, 43 and 1.11 are supported. 44 Before the release of 1.13 would be a good time 45 to upgrade your cluster to the next release. 46 So how do we upgrade? 47 Do we upgrade directly from 1.10 to 1.13? 48 No. 49 The recommended approach is 50 to upgrade one minor version at a time. 51 Version 1.10 to 1.11, then 1.11 to 1.12, 52 and then 1.12 to 1.13.

53 The upgrade process depends on how your cluster is set up. 54 For example, 55 if your cluster is a managed Kubernetes cluster deployed 56 on cloud service providers like Google for instance, 57 Google Kubernetes engine 58 lets you upgrade your cluster easily with just a few clicks. 59 If you deployed your cluster using tools like kubeadm, 60 then the tool can help you plan and upgrade the cluster.

61 If you deployed your cluster from scratch, 62 then you manually upgrade the different components 63 of the cluster yourself. 64 In this lecture, we will look at the options by kubeadm. 65 So you have a cluster with master and worker nodes, 66 running in production, hosting pods, 67 serving users. 68 The nodes and components are at version 1.10. 69 Upgrading a cluster involves two major steps. 70 First, you upgrade your master nodes 71 and then upgrade the worker nodes.

72 While the master is being upgraded, 73 the control plane components such as the API server, 74 scheduler, and controller managers go down briefly. 75 The master going down does not mean your worker nodes 76 and applications on the cluster are impacted. 77 All workloads hosted on the worker nodes continue 78 to serve users as normal. 79 Since the master is down, all management functions are down.

80 You cannot access the cluster using kube control 81 or other Kubernetes API. 82 You cannot deploy new applications or delete 83 or modify existing ones. 84 The controller managers don't function either. 85 If a pod was to fail, 86 a new pod won't be automatically created. 87 But as long as the nodes and the pods are up, 88 your applications should be up 89 and users will not be impacted. 90 Once the upgrade is complete and the cluster is back up, 91 it should function normally.

92 We now have the master and the master components 93 at version 1.11 and the worker nodes at version 1.10. 94 As we saw earlier, this is a supported configuration. 95 It is now time to upgrade the worker nodes. 96 There are different strategies available 97 to upgrade the worker nodes. 98 One is to upgrade all of them at once. 99 But then, your ports are down and users 100 are no longer able to access the applications.

101 Once the upgrade is complete, the nodes are back up, 102 new pods are scheduled and users can resume access. 103 That's one strategy that requires downtime. 104 The second strategy is to upgrade one node at a time. 105 So going back to the state where we have our master upgraded 106 and nodes waiting to be upgraded. 107 We first upgrade the first node, 108 where the workloads move to the second and third node 109 and users are served from there.

110 Once the first node is upgraded and back up, 111 we then update the second node where the workloads move 112 to the first and third nodes. 113 And finally, the third node where the workloads are shared 114 between the first two. 115 Until we have all nodes upgraded to a newer version, 116 we then follow the same procedure 117 to upgrade the nodes from 1.11 to 1.12 and then 1.13. 118 A third strategy would be to add new nodes to the cluster.

119 Nodes with newer software version. 120 This is especially convenient 121 if you're on a cloud environment 122 where you can easily provision new nodes 123 and decommission old ones. 124 Nodes with the newer software version 125 can be added to the cluster, 126 move the workload over to the new, 127 and remove the old node until you finally have all new nodes 128 with the new software version. 129 Let us now see how it is done.

130 Say we were to upgrade this cluster from 1.11 to 1.13, 131 kubeadm has an upgrade command 132 that helps in upgrading clusters. 133 With kubeadm, run the kubeadm upgrade plan command 134 and it will give you a lot of good information. 135 the current cluster version, the kubeadm tool version, 136 the latest stable version of Kubernetes. 137 Then it lists all the control plane components 138 and their versions and what version 139 these can be upgraded to.

140 It also tells you that after we upgrade 141 the control plane components, 142 you must manually upgrade the kubelet versions on each node. 143 Remember, kubeadm does not install or upgrade kubelets. 144 Finally, it gives you the command to upgrade the cluster. 145 Also note that you must upgrade the kubeadm tool itself 146 before you can upgrade the cluster. 147 The kubeadm tool also follows 148 the same software version as Kubernetes.

149 So we're at 1.11 and we want to go to 1.13. 150 But remember, we can only go one minor version at a time. 151 So we first go to 1.12. 152 First upgrade the kubeadm tool itself to version 1.12. 153 then upgrade the cluster using the command 154 from the upgrade plan output, 155 kubeadm upgrade apply. 156 It pulls the necessary images 157 and upgrades the cluster components. 158 Once complete, your control plane components 159 are now at 1.12.

160 If you run the kubectl get nodes command, 161 you will still see the master node at 1.11. 162 This is because in the output of this command, 163 it is showing the versions of kubelets 164 on each of these nodes registered with the API server 165 and not the version of the API server itself. 166 So the next step is to upgrade the kubelets. 167 Remember, depending on your setup, 168 you may or may not have kubelets running 169 on your master node.

170 In this case, the cluster deployed with kubeadm 171 has kubelets on the master node, 172 which are used to run the control plane components 173 as pods on the master nodes. 174 When we set up a Kubernetes cluster from scratch later 175 during this course, we do not install kubelet 176 on the master nodes. 177 You will not see the master node 178 in the output of this command in that case. 179 So the next step is to upgrade kubelet on the master node 180 if you have kubelets on them.

181 Run the apt-get kubelet command for this. 182 Once the package is upgraded, restart the kubelet service. 183 Running the kubectl get nodes command now shows 184 that the master has been upgraded to 1.12. 185 The worker nodes are still at 1.11. 186 So next, the worker nodes. 187 Let us start one at a time. 188 We need to first move the workloads 189 from the first worker node to the other nodes.

190 The kubectl drain command lets you safely terminate 191 all the pods from a node and reschedules them 192 on the other nodes. 193 It also cordons the node and marks it unschedulable. 194 That way no new pods are scheduled on it. 195 Then upgrade the kubeadm and kubelet packages 196 on the worker nodes as we did on the master node. 197 Then using the kubeadm tool upgrade command, 198 update the node configuration for the new kubelet version.

199 Then restart the kubelet service. 200 The node should now be up with the new software version. 201 However, when we drained the node, 202 we actually marked it unschedulable. 203 So we need to unmark it 204 by running the command kubectl uncordon node-1. 205 The node is now schedulable. 206 But remember that it is not necessary 207 that the pods come right back to this node. 208 It is only marked as schedulable.

209 Only when the pods are deleted from the other nodes 210 or when new pods are scheduled do they really come back 211 to this first node. 212 Well, it will soon come when we take down the second node 213 to perform the same steps to upgrade it. 214 And finally, the third node. 215 We now have all nodes upgraded. 216 Well, that's it for this lecture. 217 Head over to the practice test 218 where you will practice upgrading a live cluster 219 with applications running on it 220 without taking the applications down.
