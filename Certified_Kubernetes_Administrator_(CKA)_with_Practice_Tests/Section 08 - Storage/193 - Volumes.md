# Volumes

*Section: Storage*

1 Before we head into persistent volumes, 2 let us start with volumes in Kubernetes. 3 Let us look at volumes in Docker first. 4 Docker containers are meant to be transient in nature, 5 which means they are meant to last 6 only for a short period of time. 7 They're called upon when required to process data 8 and destroyed once finished. 9 The same is true for the data within the container. 10 The data is destroyed along with the container.

11 To persist data processed by the containers, 12 we attach a volume to the containers when they are created. 13 The data processed by the container 14 is now placed in this volume, 15 thereby retaining it permanently. 16 Even if the container is deleted, 17 the data generated or processed by it remains. 18 So how does that work in the Kubernetes world? 19 Just as in Docker, 20 the Pods created in Kubernetes are transient in nature.

21 When a Pod is created to process data 22 and then deleted, 23 the data processed by it gets deleted as well. 24 For this, we attach a volume to the Pod. 25 The data generated by the Pod is now stored in the volume, 26 and even after the Pod is deleted, 27 the data remains. 28 Let's look at a simple implementation of volumes. 29 We have a single-node Kubernetes cluster. 30 We create a simple Pod that generates a random number 31 between 1 and 100 32 and writes that to a file at /opt/number.out.

33 It then gets deleted along with the random number. 34 To retain the number generated by the Pod, 35 we create a volume, 36 and a volume needs a storage. 37 When you create a volume, 38 you can choose to configure its storage 39 in different ways. 40 We will look at the various options in a bit, 41 but for now, 42 we will simply configure it to use a directory 43 on the host. 44 In this case, I specify a path, /data, on the host.

45 This way, any files created in the volume 46 would be stored in the directory /data on my node. 47 Once the volume is created, 48 to access it from a container, 49 we mount the volume to a directory inside the container. 50 We use the volumeMounts field in each container 51 to mount the data volume 52 to the directory /opt within the container. 53 The random number will now be written to /opt mount 54 inside the container, 55 which happens to be on the data volume, 56 which is, in fact, the data directory on the host.

57 When the Pod gets deleted, 58 the file with the random number still lives on the host. 59 Let's take a step back 60 and look at the volume storage options. 61 We just used the hostPath option 62 to configure a directory on the host 63 as storage space for the volume. 64 Now that works fine on a single node. 65 However, it is not recommended 66 for use in a multi-node cluster. 67 This is because the Pods would use the/data directory 68 on all the nodes 69 and expect all of them to be the same 70 and have the same data.

71 Since they are on different servers, 72 they're, in fact, not the same, 73 unless you configure 74 some kind of external replicated cluster storage solution. 75 Kubernetes supports 76 several types of different storage solutions, 77 such as NFS, GlusterFS, Flocker, 78 Fiber Channel, CephFS, ScaleIO, 79 or public cloud solutions, 80 like AWS, EBS, Azure Disk or File, 81 or Google's Persistent Disk.

82 For example, to configure an AWS Elastic Block Store volume 83 as the storage option for the volume, 84 we replaced hostPath field of the volume 85 with the awsElasticBlockStore field 86 along with the volume ID and file system type. 87 The volume storage will now be on AWS EBS. 88 Well, that's it about volumes in Kubernetes. 89 We will now head over to discuss persistent volumes next.
