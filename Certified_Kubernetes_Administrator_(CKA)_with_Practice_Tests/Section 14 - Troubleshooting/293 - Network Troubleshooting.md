# Network Troubleshooting

*Section: Troubleshooting*

1 Kubernetes networking 2 is basically what lets your applications 3 or pods communicate with each other 4 with external services and with end users. 5 Now, each pod actually gets its very own unique IP address. 6 This means they can talk directly 7 without any network address translation, 8 which simplifies app design, 9 but can also make things a bit complex when things go wrong. 10 Let's quickly go over the key components.

11 First, there are pods, 12 these are your app's basic building blocks, 13 and each one gets a unique IP. 14 Then, we have services. 15 Services provide a stable way to access a group of pods. 16 Even if the underlying pods change, 17 the services address remains the same, which is nice. 18 Next up is DNS, specifically CoreDNS. 19 Think of it as the clusters phonebook. 20 It translates service names into actual IP addresses.

21 After that, we have CNI plugins. 22 These plugins are pretty critical 23 as they set up the network for your pods, 24 assigning IP addresses and configuring network interfaces. 25 And finally, we have kube-proxy. 26 This runs on every node in your cluster 27 and is responsible for keeping network rules updated. 28 These rules are what help direct traffic to your services. 29 So, when your application isn't reachable, 30 the service layer in Kubernetes 31 is a good place to start looking.

32 A Kubernetes service, remember, 33 provides a stable entry point to your pods. 34 The very first step is to verify 35 that your pods are running and healthy. 36 This is super important 37 because a service can only send traffic 38 to pods that are actually healthy and available. 39 So let's check the pods 40 associated with your host name's app. 41 You can do this with a kubectl get pods command 42 specifying the label selector.

43 This output gives us some really important information. 44 First, the Ready column tells us 1/1, 45 which means all containers within the pod 46 are ready to serve traffic. 47 The status is running, which is what we want. 48 Restarts at 0 is a good sign. 49 If you see a lot of restarts, 50 that usually points to an issue inside the pod itself. 51 Age simply shows how long the pod has been running.

52 So if your pods aren't running 53 or they have a high number of restarts, 54 the problem is likely within the pod itself. 55 In that case, you'd use kubectl logs pod name 56 or kubectl describe pod pod name to dig a bit deeper. 57 Okay, so if your pods seem healthy, 58 the next step, step two, is to try reaching them directly. 59 This is a crucial test because it bypasses the service. 60 It tells you if your application within the pod 61 is actually working on its exposed port 62 without the service layer involved.

63 So, first, you need to get your pod's IP addresses. 64 You can get those pod IPs using kubectl get pods 65 with adjacent path output. 66 For example, kubectl get pods 67 and then targeting the pod IP. 68 The output might look something like 10.244.0.5, 69 10.244.0.6, 70 10.2 44.0.7. 71 Now, once you have these IPs, you can try to curl 72 or get them directly from another pod. 73 A common way to do this 74 is to spin up a temporary busybox pod, 75 which you can do 76 with kubectl run -it --rm --restart=Never busybox 77 -image=busybox sh.

78 Once inside that busybox pod, 79 you can then try to access your application pods directly, 80 perhaps looping through those IPs. 81 If this direct connectivity works, 82 then your pods are serving traffic perfectly fine. 83 If it doesn't work, 84 then the issue lies with your application itself 85 or its container setup. 86 All right, so for step three, 87 let's check the service definition and its endpoints.

88 You need to make sure your service is not only created, 89 but also configured correctly. 90 This means the selector 91 must precisely match your healthy pod's labels. 92 Also double-check that the port for the service 93 and the target port for the pod are set correctly. 94 You can check your service definition using kubectl, 95 get service for host names, outputting in YAML format. 96 Make sure to pay close attention to the selector and ports.

97 After that, you need to check the services endpoints. 98 The Kubernetes control plane is what lists the IPs 99 and ports of all the healthy pods 100 associated with your service. 101 You can get endpoint slices for your service 102 using kubectl get endpointslices 103 with the label kubernetes.io/service-name=hostnames. 104 In the default namespace, 105 you'll see output containing the end points.

106 Now, if the end points column shows none, 107 it means your services selector 108 isn't finding any running pods. 109 In that case, you just need to double-check those labels. 110 Next up, let's tackle troubleshooting CoreDNS problems. 111 Kubernetes uses CoreDNS to resolve service names 112 to cluster IPs and pod names to IPs. 113 So, if DNS isn't working, 114 your applications literally 115 won't be able to find each other by name, 116 which is a big problem.

117 Now, let's briefly look at the CoreDNS architecture. 118 CoreDNS actually runs as pods 119 within the kube-system namespace. 120 The kube-dns service is what exposes these pods 121 and each pod's resolved dot-com file 122 points to this kube-dns service IP. 123 That's how they find it. 124 Key CoreDNS resources include a CoreDNS service account, 125 CoreDNS and kube-dns cluster roles and role bindings, 126 a CoreDNS deployment that manages the CoreDNS pods, 127 a CoreDNS config map that holds the core file configuration, 128 and finally a kube-dns service 129 which exposes CoreDNS on Port 53.

130 The core file is super important. 131 It defines exactly how CoreDNS should behave. 132 Here's a quick look at a typical core file setup. 133 This configuration basically makes CoreDNS 134 act as the backend for Kubernetes cluster domains. 135 It also forwards any out of cluster domain queries 136 to the hosts /etc/resolv.conf, 137 which then, in turn, contacts the external DNS servers. 138 Let's go through some common DNS troubleshooting steps.

139 First, you'll want to check the CoreDNS pod status. 140 You can do this with kubectl get pods 141 with the namespace set to kube-system 142 and a label selector for the kube-dns app. 143 You're hoping to see a running status there. 144 If it's pending, 145 your CNI network plugin might be the problem. 146 If you see CrashLoopBackOff, 147 it means the container is repeatedly crashing, 148 and checking the logs for the CoreDNS pods 149 will be key there.

150 Next, you need to verify the kube-dns service endpoints. 151 Use kubectl get endpointslice 152 filtering for the kube-dns service-name 153 in the kube-system namespace. 154 If you see no endpoints listed, 155 it means this service isn't finding the CoreDNS pods, 156 so you'll want to check the service selector 157 and the pod labels closely. 158 Moving on to step three, 159 inspect your pod's resolv.conf file.

160 You can check the /etc/resolv.conf 161 inside a problematic pod using kubectl exec 162 with the IT flags on your app, 163 pod name to -- cat /etc/resolv.conf. 164 The name server listed there 165 should be your kube-dns services cluster IP. 166 The search path is also important 167 as it helps resolve short names, 168 and ndots:5 is crucial 169 for how Kubernetes DNS actually works. 170 And finally, for step four, 171 test DNS resolution directly from a pod.

172 You can use nslookup from a temporary pod, 173 like a busybox pod, to test resolution. 174 For example, run kubectl exec into busybox 175 to nslookup kubernetes.default.svc.cluster.local. 176 If this command fails, then your DNS is definitely broken. 177 You should also test your actual application service name. 178 For example, 179 nslookup my-app-service.default.svc.cluster.local. 180 Now, CNI plugins are absolutely vital 181 for Kubernetes networking.

182 They're what give pods their IP addresses 183 and set up how pod-to-pod communication actually works. 184 Without a functioning CNI, 185 your pods simply can't get IPs 186 or even communicate with each other. 187 Let's look at some popular CNI plugins. 188 First, there's Flannel. 189 It's known for being simple and easy to set up. 190 It uses an overlay network, 191 which lets pods on different nodes talk to each other.

192 You can install it with a simple kubectl apply command. 193 However, it's important to note 194 that Flannel typically doesn't support 195 Kubernetes network policies on its own. 196 Then, we have Calico. 197 This is a more advanced option 198 widely recognized for its robust network policy features 199 and strong performance. 200 It can operate both with or without an overlay network. 201 Installation involves downloading a manifest 202 and then applying it with kubectl apply.

203 Calico is generally considered 204 one of the most capable CNI plugins out there today. 205 And here's a super important tip. 206 If you happen to have multiple CNI configuration files 207 in your directory, kubelet will always pick the one 208 that comes first alphabetically. 209 So if your pods are stuck in a pending state 210 or they just can't communicate at all, 211 you'll need to troubleshoot your CNI plugin.

212 First, check your CNI pods. 213 Make sure those CNI DaemonSet Pods 214 are actually running in their respective namespaces, 215 like kube Flannel or Calico system. 216 Second, check the CNI pod logs. 217 You're looking for any errors there 218 that might provide clues. 219 Next, let's talk about kube-proxy functionality 220 and debugging. 221 kube-proxy is basically a network proxy 222 that runs on every node in your cluster.

223 Its job is to make sure that traffic intended 224 for a Kubernetes service goes to the correct pod. 225 It does this by constantly watching services and endpoints 226 and then updating the network rules, 227 typically using iptables or IPVS to direct that traffic. 228 If DNS is working fine, 229 but you're still having trouble connecting to your service, 230 then kube-proxy might be the culprit.

231 Here are some troubleshooting steps for it. 232 First, you'll need to check the kube-proxy pod status. 233 Make sure all the kube-proxy DaemonSet pods 234 are running in the kube-system namespace. 235 You can use kubectl get pods in the kube-system namespace 236 filtering for the kube-proxy app. 237 Second, check the kube-proxy logs. 238 Look for any errors 239 or configuration issues present there with kubectl logs 240 for the kube-proxy pod in the kube-system namespace.

241 Third, inspect the kube-proxy configuration. 242 You should check its config map to see its settings, 243 things like its mode, 244 which could be iptables or IPVS and the clusterCIDR. 245 You can do this with kubectl get configmap 246 for kube-proxy in the kube-system namespace. 247 You can also get a look at the command it uses, 248 which often shows it pulling config 249 from files like /var/lib/kube-proxy/config.conf.

250 Lastly, a more advanced step 251 is to verify the network rules directly on the node. 252 If you're in iptables mode, 253 you can SSH into a node and inspect the iptables rules. 254 If you're using IPVS mode, 255 you'd use ipvsadm with the -ln flags. 256 Here you can see an example, ipvsadm output for a service. 257 This output clearly shows 258 how the service is load balancing traffic 259 across its various pods.

260 All right, so let's recap the key learning points 261 from this lesson. 262 First, remember that Kubernetes networking 263 relies on several core components: 264 pods, services, CoreDNS, CNI plugins, and kube-proxy. 265 When you start debugging, 266 always begin by checking the application's pod health 267 and then move on to the service's configuration 268 and its endpoints. 269 CoreDNS issues often manifest as CrashLoopBackOff, 270 pods stuck in Pending state 271 or incorrect resolv.conf entries.

272 CNI plugins are absolutely essential 273 for assigning pod IP addresses 274 and enabling pod-to-pod communication, 275 so it's critical to ensure their pods are healthy. 276 And finally, 277 kube-proxy is responsible for creating the network rules 278 that direct service traffic to pods, 279 so always inspect its status, logs, 280 and its configuration when you're troubleshooting.
