# Imperative vs Declarative

*Section: Core Concepts*

1 In this lecture, we will discuss 2 about imperative and declarative approaches in Kubernetes. 3 Towards the end of this lecture, 4 we will talk about some tips 5 that you can use in the exam. 6 So far, we have seen different ways of creating 7 and managing objects in Kubernetes. 8 We created objects directly by running commands 9 as well as using object configuration files. 10 Now, in the Infrastructure as Code world, 11 there are different approaches in managing 12 the infrastructure, and they're classified into imperative 13 and declarative approaches.

14 Let's understand these with an analogy. 15 Let's say you wanna visit a friend's house 16 located at Street B. 17 Now, in the past, you would hire a taxi 18 and give step-by-step instructions to the driver 19 on how to reach the destination, 20 like take right to street B, 21 then take left to go to street C, 22 and then take another left, and then right to go to Street D 23 and stop at the house.

24 Specifying what to do 25 and how to do more importantly, is the imperative approach. 26 On the other hand, today when you book a cab, say 27 through Uber, you just specify the final destination, 28 like drive to Tom's house, 29 and this is the declarative approach. 30 In this case, we're not giving step-by-step instructions. 31 Instead, we're just specifying the final destination. 32 We're declaring the final destination, 33 and the system figures out the right path 34 to reach the destination.

35 Specifying what to do, 36 not how to do is the declarative approach. 37 So what's that got to do with what we are learning? 38 In the Infrastructure as Code world, 39 an example of an imperative approach 40 of provisioning infrastructure would be a set 41 of instructions written step by step, 42 such as provisioning a VM named a web server, 43 installing the Nginx software on it, 44 editing configuration file to use port 8080 45 and setting the path to web files, downloading source code 46 of repositories from Git, 47 and finally starting the Nginx server.

48 So here we're saying what is required 49 and also how to get things done. 50 In the declarative approach, we declare our requirements. 51 For instance, all we say is that we need a VM 52 by the name Web Server with the internet software on it, 53 with a port set to 8080 54 and the path to the web files defined 55 and where the source code of the application is stored, 56 and everything that's needed to be done 57 to get this infrastructure in in place is done 58 by the system or the software.

59 You don't have to provide step-by-step instructions. 60 Orchestration tools like Ansible, Puppet or Chef 61 or Terraform fall into this category. 62 In the imperative approach, 63 what happens if the first time only half 64 of the steps were executed? 65 What happens if you provide the same set 66 of instructions again to complete the remaining steps? 67 To handle such situations, 68 there will be many additional steps involved, such as checks 69 to see if something already exists 70 and taking an action based on the results of that check.

71 For instance, while provisioning a VM, 72 what would happen if a VM 73 by the name Web Server already exists? 74 The same goes with creating a database or importing data. 75 Should it fail or should it continue 76 since the VM is already there? 77 What if we decide to upgrade the version of software 78 to say Nginx 1.18 in the future? 79 It should be as simple 80 as updating the version of Nginx in the configuration file, 81 and the system should take care of the rest.

82 Ideally, the system should be intelligent enough to know 83 what has already been done 84 and apply the necessary changes only. 85 That's the declarative way of doing things. 86 In the Kubernetes world, the imperative way 87 of managing infrastructure is using commands 88 like the kubectl run command to create a pod, 89 the kubectl create deployment command 90 to create a deployment, the kubectl expose command 91 to create a service to expose a deployment, 92 and the kubectl edit command may be used 93 to edit an existing object.

94 For scaling a deployment or replica set, 95 use the kubectl scale command, 96 and updating the image on a deployment, 97 we use the kubectl set image command. 98 Now, we have also used object configuration files 99 to manage objects 100 such as creating an object 101 using the kubectl create -f command with the F option 102 to specify the object configuration file, 103 and editing an object using the kubectl, replace command 104 and deleting an object using the kubectl delete command.

105 All of these are imperative approaches 106 to managing objects in Kubernetes. 107 We're saying exactly how to bring the infrastructure 108 to our needs by creating, updating or deleting objects. 109 The declarative approach would be to create a set of files 110 that defines the expected state of the applications 111 and services on a Kubernetes cluster, 112 and with a single kubectl apply command, 113 Kubernetes should be able to read the configuration files 114 and decide by itself what needs to be done 115 to bring the infrastructure to the expected state.

116 So in the declarative approach, 117 you will run the kubectl apply command for creating, 118 updating or deleting an object. 119 The apply command will look at the existing configuration 120 and figure out what changes need to be made to the system. 121 So let's look at these in a bit more detail. 122 Now, within the imperative approach, there are two ways. 123 The first is using imperative commands such as the run, 124 create or expose commands to create new objects 125 and the edit, scale and set commands 126 to update existing objects.

127 Now, these commands help in quickly creating 128 or modifying objects as we don't have to deal 129 with YAML files. 130 And these are helpful during the certification exams. 131 However, there are limited in functionality 132 and will require forming long 133 and complex commands for advanced use cases 134 such as creating a multi-container pod or deployment. 135 Secondly, these commands are run once and forgotten.

136 They're only available in the session history of the user 137 who ran these commands, 138 so it's hard for another person to figure out 139 how these objects were created. 140 So it is hard to keep track of. 141 And so it's difficult to work with these commands in large 142 or complex environments. 143 And that's where managing objects 144 with object configuration files can help. 145 Creating object definition files or configuration files 146 or manifest files, as it's also called, 147 can help us write down exactly what we need the object 148 to look like in a YAML format 149 and use the kubectl create command to create the object.

150 We now have the YAML file with us always, 151 and it can be saved in a code repository like Git. 152 We can put together a change review 153 and approval process around these files 154 so that a change made is reviewed and approved 155 before it is applied to a production environment. 156 In the future, if a change is to be made, for instance, 157 editing the image name to another version, 158 there are different ways to go about it.

159 One way is to use the kubectl edit command 160 and specify the object name. 161 So when this command is run, 162 it opens a YAML definition file similar to the one you used 163 to create the object, 164 but with some additional fields such as the status fields 165 that you see here, which are used 166 to store the status of the pod. 167 This is not the file you used to create the object. 168 This is a similar pod definition file 169 within the Kubernetes memory.

170 You can make changes to this file and save and quit, 171 and those changes will be applied to the live object. 172 However, note that there is a difference 173 between the live object 174 and the definition file that you have locally. 175 The change you made using the kubectl edit command 176 is not really recorded anywhere. 177 After the change is applied, you're only left 178 with your local definition file, 179 which in fact has the old image name in it.

180 In the future, say you 181 or a teammate decide to make a change to this object 182 unaware that a change was made 183 using the kubectl edit command, 184 when the new change is applied, the previous change 185 to the image is lost. 186 So you can use the kubectl edit command 187 if you are making a change 188 and you're sure that you're not going 189 to rely on the object configuration file in the future.

190 A better approach to that is to first edit the local version 191 of the object configuration file with the required changes. 192 That is by updating image name here, 193 and then running the kubectl replace command 194 to update the object. 195 This way, going forward, the changes made are recorded 196 and can be tracked as part of the change review process. 197 So at times you may want to completely delete 198 and recreate objects.

199 In such cases, you may run the same command, 200 but with the force option like this. 201 Now, this is still the imperative approach 202 because you're still instructed Kubernetes how to create 203 or update these objects. 204 First, you run the kubectl create command 205 to create the object, and then you run the replace command 206 to replace the object or delete command 207 to delete the object.

208 And what if you run the create command 209 if the object already exists? 210 Well, then it would fail 211 with an error that says the pod already exists. 212 When you update an object, you should always make sure 213 that the object exists first 214 before running the replace command. 215 If an object does not exist, the replace command fails 216 with an error message. 217 So the imperative approach is very taxing for you 218 as an administrator as you must always be aware 219 of the current configurations 220 and perform checks to make sure that things are in place 221 before making a change.

222 The declarative approach is where you use 223 the same object configuration files 224 that we've been working on, but instead of the create 225 or replace commands, we use the kubectl apply command 226 to manage objects. 227 The kubectl apply command is intelligent enough 228 to create an object if it doesn't already exist. 229 If there are multiple object configuration files 230 as you would usually, then you may specify a directory 231 as the path instead of a single file.

232 That way, all the objects are created at once. 233 Now, when changes are to be made, 234 we simply update the object configuration file 235 and run the kubectl apply command again, 236 and this time it knows that the object exists, 237 and so it only updates the object with the new changes. 238 So it never really throws an error 239 that says the object already exists 240 or the updates cannot be applied.

241 It'll always figure out the right approach 242 to updating the object. 243 So going forward, any changes made on the application, 244 whether they're updating images 245 or fields of existing configuration files 246 or adding new configuration files altogether 247 for new objects, all we do is simply update 248 our local directory with the changes, 249 and then the kubectl apply command take care of the rest.
