# TLS in Kubernetes - Certificate Creation

*Section: Security*

1 In this lecture, 2 we'll look at how to generate the certificates 3 for the cluster. 4 To generate certificates, 5 there are different tools available, 6 such as EasyRSA, OpenSSL, or CFSSL, et cetera, 7 or many others. 8 In this lecture, we will use OpenSSL tool 9 to generate the certificates. 10 This is where we left off. 11 We will start with the CA certificates. 12 First, we create a private key using the OpenSSL command, 13 "openssl genrsa -out ca.key." 14 Then we use the OpenSSL request command 15 along with the key we just created 16 to generate a certificate signing request.

17 The certificate signing request is like a certificate 18 with all of your details, but with no signature. 19 In the certificate signing request, 20 we specify the name of the component this certificate is for 21 in the common name or CN field. 22 In this case, since we are creating a certificate 23 for the Kubernetes CA, we name it "KUBERNETES-CA." 24 Finally, we sign the certificate using 25 the openssl x509 command 26 and by specifying the certificate signing request 27 we generated in the previous command.

28 Since this is for the CA itself, 29 it is self signed by the CA using its own private key 30 that it generated in the first step. 31 Going forward, for all other certificates, 32 we will use this CA key pair to sign them. 33 The CA now has its private key and root certificate file. 34 Great. 35 Let's now look at generating the client certificates. 36 We start with the admin user. 37 We follow the same process 38 where we create a private key for the admin user 39 using the OpenSSL command, we then generate a CSR.

40 And that is where we specify the name of the admin user, 41 which is kube-admin. 42 A quick note about the name. 43 It doesn't really have to be kube-admin, 44 it could be anything. 45 But remember, this is the name 46 that kube control client authenticates with 47 and when you run the kubectl command. 48 So in the audit logs and elsewhere, 49 this is the name that you will see. 50 So provide a relevant name in this field.

51 Finally, generate a signed certificate using 52 the openssl x509 command. 53 But this time, you specify the CA certificate 54 and the CA key. 55 You're signing your certificate with the CA pair. 56 That makes this a valid certificate within your cluster. 57 The signed certificate is then output to admin.crt file. 58 That is the certificate that the admin user will use 59 to authenticate to Kubernetes cluster.

60 If you look at it, this whole process of generating a key 61 and a certificate pair is similar 62 to creating a user account for a new user. 63 The certificate is the validated user ID 64 and the key is like the password. 65 It's just that it's more secure 66 than a simple username and password. 67 So this is for the admin user. 68 How do you differentiate this user from any other users? 69 The user account needs to be identified as an admin user, 70 and not just another basic user.

71 You do that by adding the group details 72 for the user in the certificate. 73 In this case, a group named "SYSTEM:MASTERS" 74 in system Kubernetes with administrative privileges. 75 We will discuss about groups later, 76 but for now, it's important to note 77 that you must mention this information 78 in your certificate signing request. 79 You can do this by adding group details 80 with the OU parameter 81 while generating a certificate signing request.

82 Once it's signed, we now have our certificate 83 for the admin user with admin privileges. 84 We follow the same process to generate client certificates 85 for all other components that access the Kube-API server. 86 The kube-scheduler. 87 Now, the kube-scheduler is a system component part 88 of the Kubernetes control pane. 89 So its name must be prefixed with the keyword SYSTEM. 90 The same with kube controller manager, 91 it is again, a system component.

92 So its name must be prefixed with the keyword system. 93 And finally, kube-proxy. 94 So far, we have created CA certificates, 95 then all of the client certificates, 96 including the admin user, scheduler, 97 controller manager and kube proxy. 98 We will follow the same procedure 99 to create the remaining three client certificates 100 for API servers and kubelets 101 when we create the server certificates for them.
