# Docker Init

*Section: Docker Images*

1 Writing a Docker file from scratch is a perfectly fine skill to have, but for a brand new project 2 where you just want something that works to start from, Docker has a built-in scaffolder that does 3 most of the boilerplate for you. It's called Docker init and that's what we're going to look 4 at in this lecture. So what does Docker init do? You cd into a project directory, you run Docker 5 init and it walks you through a short interactive prompt. It looks at the files in your project, 6 guesses what language you're using, package.json means node, go.mod means go, requirements.txt 7 means python and so on and asks you to confirm. Then depending on the language, it asks a few 8 follow-up questions. What runtime version? What package manager? Which file is the entry point?

9 What port should the app listen on? Three or four short answers and you're done. What you get back 10 is four files. The first is a Docker file written using current best practices, a multi-stage build, 11 a slim base image, a non-root user and the layers ordered so that dependencies cache well. The second 12 is a dot dockerignore, pre-populated with sensible entries for your language, node underscore modules 13 for node, double underscore pycache, double underscore for python, target for rust, that kind 14 of thing. The third is a compose dot yaml, a starter compose file that defines a single service 15 with your port mapped. And the fourth is a readme.docker.md with a short guide on how to 16 build and run the thing. Four files generated in a few seconds, all sitting next to your application 17 code, ready to be edited. Now a few words on what Docker init actually is. It's a template 18 scaffolder, not an AI tool. The CLI ships with a small set of static templates, one per supported 19 language, and it fills in the blanks based on your answers. It doesn't read your source code, so it 20 doesn't know about your custom build steps, your environment variables or any libraries you're 21 importing that might need extra system packages on the base image. The Docker file it produces 22 is a sensible starting point for a typical app in your language, not a finished solution for your 23 specific app. Most projects need at least a few hand edits afterward, adding system dependencies 24 in the build stage, setting environment variables or adjusting the entry point if it isn't quite 25 what you told it. So treat the output the same way you treat a create react app or a cargo new, it's 26 a starting line, not a finish line. The supported languages are the ones you'd expect for a starter 27 tool, Go, Python, Node, Rust, ASP.NET Core, PHP with Apache and Java. If your project is something else, you 28 can still pick the other option and it'll drop a minimal generic Docker file in place that you fill 29 out yourself. One more thing worth knowing, if a dockerfile.dockerignore or compose.yaml already 30 exists in the directory, Docker init will ask before overwriting any of them. So you can safely run it 31 in a project that already has some Docker assets without losing your work. When is Docker init 32 worth using? Pretty much anytime you're starting a new project from scratch and you don't already 33 have a Dockerfile template you like. It saves you a few minutes of typing and it nudges you toward 34 the patterns Docker itself recommends. Multi-stage builds, slim images, non-root users, which are easy 35 to forget when you're writing one from memory. When is it not the right tool? When you already have a 36 Dockerfile that works or when your project has unusual requirements that the templates don't 37 cover. At that point, you're better off writing the Dockerfile by hand or copying one from a 38 similar project you've worked on.
