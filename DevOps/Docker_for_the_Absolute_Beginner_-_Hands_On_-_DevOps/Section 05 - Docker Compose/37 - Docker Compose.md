Let's look at 39 a better example. We're going to use 40 the same sample voting application that everyone 41 uses to demonstrate Docker.

42 It's a simple yet comprehensive application 43 built to showcase how an application stack 44 runs on Docker. We'll be working 45 with this same application throughout the rest of the 46 course, so let's get familiar with it. 47 The sample voting application provides 48 one interface for a user to vote and another 49 interface to show the results. 50 The voting app is a web 51 application written in Python that gives the 52 user an interface to choose between two 53 options, a cat or a dog.

54 When you make a selection, the vote 55 is stored in Redis. 56 For those of you who are new to Redis, in this case 57 Redis serves as an in-memory database. 58 The vote is then processed by the worker, 59 which is an application written in .NET. 60 The worker takes the new vote and 61 updates the persistent database, which is 62 PostgresQL in our case. 63 Postgres simply has a table with the number of 64 votes for each category, cats and dogs, 65 and the worker increments the count for 66 whichever option was chosen.

67 Finally, the result of the vote is displayed 68 in another web interface, 69 this one built in Node. 70 The result app reads the vote count 71 in PostgresQL and displays it to the user. 72 That is the architecture and 73 data flow of this voting application 74 stack. As you can see, the sample 75 is built with a combination of 76 different services and different development 77 platforms, Python, Node, 78 .NET, Redis, and PostgresQL.

79 This is going to showcase 80 how easy it is to set up an entire 81 application stack made of diverse 82 components on Docker. 97 Hold that thought, we'll come back to it. 98 Next, deploy the PostgresQL database. 99 Again, run it in the background and name this container 100 db. Next, we move on 101 to the application services. Deploy 102 the front-end voting interface by running an instance 103 of the voting app image 104 named vote. Since this is a web 105 server with a UI on port 80, 106 publish that port to 5000 on the host 107 so we can access it from a browser.

108 Then deploy the result web application 109 that shows the results to the user 110 mapping its port 80 to host 111 port 5001. Finally, 112 deploy the worker. 113 All the instances are running on 114 the host, but there's a problem. It just 115 doesn't seem to work. 116 We have successfully run all the 117 different containers, but we haven't actually 118 linked them together. We haven't told the voting 119 web app to use this particular Redis instance.

120 There could be multiple Redis instances 121 running. We haven't told the worker 122 and the result app to use this particular 123 Postgres database. So how 124 do we do that? The original 125 answer was a command line option 126 called dash dash link. For example, 127 the voting app web service is dependent 128 on Redis. When the web 129 server starts, it looks in its code for a host 130 called Redis, but the voting app container 131 cannot resolve that name on its own.

132 To make the voting app aware of 133 Redis, you would add a dash dash link 134 flag pointing at the Redis container, which 135 adds an entry to the container's etc host 136 file mapping the name Redis to Redis' internal 137 IP. That is also why we 138 named the container in the first place, so 139 we could refer to it by name when creating the 140 link. The same approach applied to the 141 result app linking to the database and 142 the worker needing two links, one to Redis 143 and one to Postgres. Note that 144 using dash dash link this way 145 is deprecated and support may be removed 146 in future Docker versions.

147 The reason is that newer concepts 148 in Docker networking offer better ways of doing 149 exactly what links did. 150 The modern replacement is a user 151 defined network. Containers attached 152 to the same user defined network 153 resolve each other by container 154 name automatically. No extra flag 155 needed. Mention Redis in your 156 code and Docker's built-in DNS 157 handles the lookup. Compose actually 158 creates one of these networks for you 159 by default, which we'll see in a moment.

160 Once we have the Docker run commands tested 161 and ready, it is easy to generate 162 a Docker Compose file from them. 163 We start by creating a dictionary of 164 container names using the same names 165 we used in the Docker run commands. 166 Take all the names and create a key 167 for each. Then, under 168 each item, specify which image 169 to use. The key is image and the value 170 is the image name. Next, 171 inspect the commands and see what other 172 options were used. We published ports 173 so move those ports under the respective 174 containers. Create a ports property 175 and list every port you want to publish 176 under it. Now we are all done 177 with the Compose file and bringing up the stack 178 is really simple. One command to bring up the entire 179 application stack. Compose 180 creates a default network for the project 181 so the services resolve each other by service name 182 automatically. No links entries 183 needed. Now let's 207 look at the different versions 208 of the Compose file. 209 This is important because you might see 210 Compose files in different formats in different 211 places and wonder why some look different.

212 Compose evolved over time 213 and now supports a lot more options 214 than it did in the beginning. The original 215 format known as version 1 216 listed services directly at 217 the root of the file. 218 It had a number of limitations. For example, 219 there was no way to deploy containers 220 on a network other than the default bridge 221 and there was no way to specify a 222 startup order. Version 1 is 223 legacy and should not be used in new 224 files. Support for those missing 225 features came in version 2. With 226 version 2 and up, the format changed.

227 You no longer specified your stack 228 information directly at the root. 229 Everything was encapsulated in a 230 services section. You also had to declare 231 the version at the top of the file so Compose 232 knew which format you were using. 233 Version 2 also introduced two 234 important things. Compose started 235 creating a dedicated bridge network 236 for each project so containers could 237 talk to each other by service name without links 238 and a new depends on property let you 239 say, for example, that the voting 240 application is dependent on Redis. So 241 Redis comes up first. Version 2 242 is also legacy today.

243 Then came version 3, similar in structure to 244 version 2, version key at the top, 245 services section under it. 246 Version 3 added support for Docker Swarm, 247 removed some options and added 248 others. Version 3 is the last 249 of the legacy formats and is also 250 no longer recommended for new files. 251 Today, the current standard is the Compose 252 specification and that is 253 what you should write. There is no 254 version key. That field has been obsolete 255 since Compose specification v2.25 in March 2024.

256 Files start directly 257 with services. Compose creates a 258 default network for the project. Services 259 resolve each other by service name and 260 features like depends on and profiles are 261 available out of the box. 262 Let's talk about networks in Compose. 263 So far we have been deploying 264 all containers on the default network Compose 265 creates for us. Suppose we 266 modify the architecture a little to contain 267 traffic from different sources.

268 For example, we want to separate 269 user-generated traffic from the 270 application's internal traffic. We create 271 a front-end network dedicated to user 272 traffic and a back-end network dedicated 273 to internal communication. 274 We then connect the user-facing 275 applications, the voting app 276 and the result app to the front-end network 277 and connect all components to the 278 back-end network. The first thing we need 279 to do if we want to use custom networks is 280 to define the networks we are going 281 to use. In our case, we have 282 two front-end and back-end. Create a 283 top-level networks property at the root of the 284 Compose file and list the networks under it.

285 Then under each service, add a networks 286 property and provide a list of networks that 287 service should attach to. For Redis 288 and the database, that's only the 289 back-end network. 290 For the voting app and result app, 291 they need both front-end and back-end. 292 The worker also goes on the back-end network. 293 Now Redis and the database are only on 294 the back-end network. The public-facing apps 295 reach them, but nothing from outside 296 can. That's the conceptual tour.
