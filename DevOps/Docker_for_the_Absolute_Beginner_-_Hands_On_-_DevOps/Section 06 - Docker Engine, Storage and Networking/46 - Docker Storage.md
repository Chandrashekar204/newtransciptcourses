# Docker Storage

*Section: Docker Engine, Storage and Networking*

1 Let us start with how docker stores data on the local file system. 2 When you install docker on a system, it creates a folder structure 3 at slash var slash lib slash docker. Underneath, you have multiple folders, 4 containers, image, volumes, and on a modern install, overlay 2. 5 This is where docker stores all its data by default. When I say data, I mean 6 files related to images and containers running on the docker host.

7 Files for containers live under the containers folder. Files for images 8 live under the image folder. And any volumes created by docker containers 9 are created under the volumes folder. Don't worry about volumes for now, we 10 will come back to them in a bit. So how exactly does docker store the 11 files of an image and a container? To understand that, we need to look at 12 docker's layered architecture. When docker builds images, it builds 13 them in layers. Each line of instruction in the docker 14 file creates a new layer in the image with just the changes from the previous 15 layer. The first layer is a base ubuntu 16 operating system. The second instruction creates a second layer that installs all 17 the apt packages. The third creates a layer with the 18 python packages. The fourth copies the source code over 19 and the fifth updates the entry point of the image.

20 We build this image with docker build with the dash t flag 21 for mmshud slash my custom app from the current directory. Since each 22 layer only stores the changes from the previous layer, this is reflected 23 in the size as well. The base ubuntu image is around 120 24 megabytes. The apt packages add about 300 megabytes. 25 The remaining layers are small. To understand the advantage of this layout, 26 consider a second application. Different docker file but very similar to 27 the first. Same ubuntu base, same python and flask 28 dependencies, just a different source file and a different entry point.

29 When I build the second image, the first three layers are identical to the first 30 application so docker doesn't rebuild them. 31 It reuses the same three layers from the cache and only creates the last two 32 layers with the new source and the new entry 33 point. This way docker builds images faster and saves disk space. 34 The same thing happens when you update your application code. 35 Docker reuses every prior layer from cache and only rebuilds 36 the layer that changed which saves a lot of time during rebuilds and updates.

37 If we rearrange the layers bottom up, it's easier to see. At the bottom, the 38 base ubuntu layer, then the packages, then the dependencies, 39 then the source code and on top the entry point. 40 All of these are created when you run the build command and together they form 41 the final docker image. These are the image layers. Once the 42 build is complete, you cannot modify the contents of these layers.

43 They are read only. The only way to change them 44 is to start a new build. When you run a container from this image, 45 docker creates a new writable layer on top of the image layers. 46 This writable layer is where the container stores anything it creates 47 at runtime, log files written by the application, 48 temporary files or any file modified by a user inside the container. 49 The life of this layer is only as long as the container is alive.

50 When the container is destroyed, this layer and everything in it is destroyed 51 too. The same image layers are shared by every 52 container created from this image. Only the writable layer is unique per 53 container. If i log in to the new container and 54 create a file called temp.txt, that file lives in the 55 writable container layer. Now what about the application code 56 which is part of the read only image layer? Can i still modify it?

57 Yes. But before the modified file is saved, docker automatically copies the 58 file from the image layer up into the read write layer and you end 59 up editing that copy. All future modifications happen on the 60 copy in the writable layer. This is called 61 the copy on write mechanism. The image stays read only. The original file is 62 never touched and the image remains the same all the time 63 until you rebuild it. When the container is removed, the 64 writable layer goes with it. The change to the application code and 65 the new temp.txt are gone. So what if we want to keep that data?

66 For example, if we were running a database and we needed to preserve what 67 the container wrote, we could attach a persistent volume. To 68 do that, first create a volume with docker volume create data volume. 69 This creates a folder called data volume under slash var slash lib 70 slash docker slash volumes. Then when you run a container you mount that volume 71 into the container's read write layer using the dash v option.

72 The volume name goes on the left, the path inside the container goes on the 73 right. For mysql, the default data path is 74 slash var slash lib slash mysql. That's where mysql 75 writes its data. So we run docker run with the dash v flag 76 mapping data volume to slash var slash lib slash mysql 77 in a mysql container. This creates a new container and mounts data volume into 78 the mysql data directory inside the 79 container. All data written by the database is in 80 fact stored on the volume on the docker host. Even if 81 the container is destroyed, the data is still there. Now what if you 82 didn't run docker volume create first? If you run a mysql 83 container with a volume name that doesn't exist yet, 84 docker will automatically create the volume and mount it for you.

85 You'll see it if you list the contents of the volumes folder under 86 slash var slash lib slash docker. This is called 87 volume mounting. Docker creates and manages the volume under its own 88 directory. But what if your data already lives 89 somewhere else? Say you have external storage on the docker host at slash data 90 and you want the database to write there instead of 91 the default volumes folder. In that case, you provide the full host path to the 92 folder you want to mount. Docker run with the dash v flag mapping 93 slash data slash mysql to the same target in a mysql 94 container. This is called a bind mount. So we have two types of mounts. Volume 95 mount mounts a volume from the volumes directory and bind 96 mount mounts a directory from any location on the 97 docker host. One final point. Using the dash v form 98 is the old style. The new way is to use the mount option which is more explicit 99 and supports advanced features that the dash v form cannot.

100 With the mount option, you spell out each parameter as a key 101 equals value pair. These advanced features include setting volume driver 102 options, mounting a subdirectory of a volume and 103 mounting a volume into a swarm service. The bind mount above can be written with 104 the mount option as docker run with the mount option 105 type equals bind source equals slash data slash mysql. Target equals 106 the mysql data directory in a mysql container.

107 The type is bind. Source is the location on the host 108 and target is the location inside the container. So who is responsible for all 109 of these operations? Maintaining the layered 110 architecture, creating the writable layer, copying files between layers for 111 copy on write is the storage driver. Docker uses storage drivers to make the 112 layered architecture work. On a modern linux host, the classic 113 drivers are overlay2, btrfs, zfs, 114 fuse overlay fs for rootless docker on older kernels 115 and vfs. For a long time, overlay2 was the default on every modern linux 116 distribution. Use btrfs if slash var slash lib slash 117 docker sits on a btrfs file system, zfs if it sits on zfs, 118 fuse overlay fs for rootless setups on kernels without overlay support and vfs 119 only for testing. It has no copy on write. You may run into older material that 120 mentions aufs, device mapper or a legacy overlay 121 driver. Those have all been removed. Aufs and 122 legacy overlay v1 were removed in docker engine v24.0 123 and device mapper was removed in v25.0.

124 Docker selects the storage driver automatically based on the operating 125 system. So in practice, you rarely have to think 126 about it. There's one more thing that changed recently. Remember from the 127 previous lesson that docker hands the real container work to container d 128 underneath. Starting with docker engine v29.0, 129 container d also owns image storage on fresh installs. 130 Instead of docker maintaining its own image store under slash var slash lib 131 slash docker slash image and using a storage driver like overlay 132 2, it uses container d's image store with 133 pluggable components called snapshotters. The default snapshotter is still overlay 134 fs, so the same linux overlay file system 135 you've always used is still doing the work 136 underneath. What changed is the layer above it. The reason this matters 137 is that the container d image store unlocks features the old setup couldn't 138 easily do. Multi-arc images stored locally, 139 image signatures and attestations alongside the image, 140 web assembly containers and lazy pulling snapshotters that stream layers 141 on demand. If you installed docker before v29.0 and 142 upgraded, you're still on the classic overlay 2 143 setup until you opt in. If you installed docker fresh recently, 144 you're probably already on the container d image store and 145 never noticed. Same docker pull, same docker run, same images on disk, just a 146 different owner.
