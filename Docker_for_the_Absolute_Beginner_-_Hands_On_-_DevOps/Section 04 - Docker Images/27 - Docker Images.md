35 It's in an instruction and arguments format. 36 For example, in this Dockerfile, everything on the left in caps 37 is an instruction. In this case, from, run, copy, 38 env, and entry point are all instructions, and each of these tells Docker to 39 perform a specific action while creating the image. Everything on 40 the right is an argument to those instructions. The first line 41 from Ubuntu defines what the base OS should be for 42 this container. 47 The run instruction tells Docker to run a particular command on the base image. 48 So at this point, Docker runs apt-get update to fetch the updated package list 49 and then installs flask on the image. Then the copy instruction copies files 50 from the local system onto the Docker image. 51 In this case, I'm copying my application file app.pi 52 into the location slash opt inside the Docker image.

53 The env instruction sets an environment variable inside the image. 54 Here we set flask app to point at the location of our application. 55 And finally, entry point lets us specify the command that will be run 56 when the image is run as a container. Now when Docker builds the image, 57 it builds it in a layered architecture. Each line of instruction creates a new 58 layer in the Docker image with just the changes 59 from the previous layer. For example, the first layer is the base 60 Ubuntu OS, followed by a second layer that runs 61 apt-get update, followed by a third layer that installs 62 flask. Then comes a layer that copies the source code over, 63 a layer that sets the environment variable, and a final layer that updates 64 the entry point of the image. Since each layer 65 only stores the changes from the previous layer, 66 this is reflected in the size as well. If you look at the 67 base Ubuntu image, it is around 120 megabytes in size. The flask install is 68 around 50 megabytes. And the remaining layers are small. You 69 can see this information by running the docker history command 70 followed by the image name. When you run docker build, you can see 71 the various steps involved and the result of 72 each step. Here's what that looks like in practice. All the layers built are cached 73 so the layered architecture helps you restart the build from a particular step 74 in case it fails. Or if you were to add new steps in the 75 build process, you wouldn't have to start all over 76 again. So in case a particular step was to fail, for example, step three failed 77 and you fix the issue and rerun docker build, it will reuse the previous layers 78 from cache and continue to build the remaining layers. The same is true if you 79 were to add additional steps in the docker file.

80 This way, rebuilding your image is faster and you don't have to wait for 81 docker to rebuild the entire image each time. 82 This is helpful especially when you update the source code of your 83 application, which may change more frequently.
