Kind: captions Language: en Now that you've seen how Java uses Locale to customize the display of dates and currencies, it's time to learn how you can design your own application, to allow Locale specific elements to be used. This starts with the ResourceBundle class. The ResourceBundle class is an abstract class in the java.util package. You can implement classes that extend this abstract class. Or, You can get an instance of a ResourceBundle, by calling one of several static getBundle methods, on the ResourceBundle class.

The latter approach is dependent on resource data, either stored in a series of files, or provided by a service. Data that's customized is often textual, in the form of user messages, button labels or menu items, but may contain other elements such as images or audio components. To date, the most common method of supplying data for a ResourceBundle, is using the properties file. This is a simple text file, containing key value pairs. The key is a string, a name to be used when the data is requested, and the value is also a single text literal.

The properties file name includes a base name, called the bundle name and some part of the Locale identifier, and ends with the extension .properties. For example, you could have a default properties file, called TextMessages.properties, which might describe strings for basic interface language elements, like yes, no, hello, world and so on. yes = yes no = no hello = hello world = world Here, I'm showing an example of a base TextMessages properties file.

You'll create additional properties files, to support other languages. You can think of a bundle as a series of files that have the same base bundle name but are differentiated by Locale specifics. If you need to support the spanish language for example, you would create a TextMessages_es.properties file, with spanish language text literals for yes, no, hello and so on. I show an example of this file here. Notice that the keys for both these properties files are in English, and are the same for both files.

Whatever language you choose for your keys is up to you, but they do need to be consistent across files, so that the key can be used to look up the value. yes = si no = no hello = hola world = mundo Of course, there are many language dialects, so you may need to also provide additional language variations for these, which can be done by including country, script and or a variant. The makers of IntelliJ, JetBrains, have a plug-in feature available called the Resource Bundle editor, that can help you manage these series of files, and the data they contain.

Java has specific rules for searching and matching one of these properties files, to a Locale. These rules can be found in the ResourceBundle class documentation. This method will construct a series of candidate names, which are shown here using the Locale to find the best matching properties file it can. The base file is always the last in the chain, and will get returned if no other matches were found. This hierarchy lets you design your language elements broadly, at just the language level, to much more specific and targeted elements.
