First a server socket is a blocking io, and you saw that in a previous video, The server application blocked while waiting to connect to a client when calling the accept method. We added a timeout to try to reduce the effect of this issue.

We then used threads to increase efficiency when reading the requests, but this doesn't completely solve the problem since all your threads could be stuck waiting to connect to a client. The server socket channel can be non-blocking so it doesn't block a thread when an accept method is called. This means a single thread can handle multiple connections without threading. By including this architecture in a multi threaded server, you're exponentially increasing your throughput.

For this reason the server socket channel is more scalable than the server socket. In addition the server socket supports only TCP connections, but the server socket channel handles many different protocols. The server socket channel has other advantages as shown on this slide. The server socket channel supports both stream based data and datagrams, which I'll be covering a bit later. Obviously with non-blocking IO, you could expect better performance from the server socket channel.

For servers with low to moderate traffic the server socket might be sufficient for your needs. But learning how to use the server socket channel will help you to write high-performance servers, with numerous concurrent connections, low latency and efficient resource management.
