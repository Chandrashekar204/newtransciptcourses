So we use commit from this point forward. Now database transactions must be acid compliant. They must meet the following characteristics. So the a in asset stands for atomicity. Now this relates to what we've just discussed. If a series of SQL statements change the database, then either all the changes are committed or none of them are. The second letter c stands for consistency. Before a transaction begins, the database is in a valid state. When it completes, the database is still in a valid state.

The i in asset stands for isolation. So until the changes committed by a transaction are completed, they won't be visible to other connections. So transactions can't depend on each other. And lastly, the d in asset stands for durability. Once the changes performed by transaction are committed to the database, they're permanent. Now if an application then crashes or the database server goes down in the case of a client server database like MySQL for example.

The changes made by the transactions are still there when the application runs again, or the database comes back up. So essentially, transactions ensure the integrity of the data within a database. Now we only have to use transactions when we change the data in a database. We don't need them if we're querying the database since we're not changing any data.
