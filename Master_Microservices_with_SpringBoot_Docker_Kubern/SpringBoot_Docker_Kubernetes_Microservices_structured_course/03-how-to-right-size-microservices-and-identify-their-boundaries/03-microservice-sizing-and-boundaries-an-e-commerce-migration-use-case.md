# 3.3 — Microservice Sizing & Boundaries: An E-Commerce Migration Use Case

> Section 3: How to Right-Size Microservices & Identify Their Boundaries

So far, we have spent quite some time understanding what right-sizing is and how organizations identify the boundaries of their microservices. Now, it's time to answer another important question. Why does right-sizing matter so much? To understand that, let's walk through a real-world migration scenario. Imagine a fast-growing e-commerce startup. In its early days, the company built a simple monolith application. It served its purpose perfectly because the development team was small, the number of customers are limited, and new features could be delivered quickly.

At that stage, there was absolutely nothing wrong with choosing a monolithic architecture. Let's see how that application looked. The startup had a single backend server. This backend exposed APAs that were consumed by mobile application and website. At the same time, the startup had a single backend server. This backend exposed APIs that were consumed by mobile application. At the same time, it also supported a traditional MVC-based web application for its website.

So mobile clients communicated using REST APIs while the web application used the MVC pattern to interact with the same backend. Inside this multi-application, all the business modules were packaged and deployed together. For example, the application contained modules such as identity, catalog, orders, invoices, sales, marketing, and so on. You can imagine many more modules, but for simplicity, let's work with these six. All these modules shared a single relational database, which is typical in a monolithic architecture.

During the initial stages of the company, this architecture worked extremely well. The application was easy to build, easy to test, easy to deploy, easy to troubleshoot. With only a handful of developers and a small customer base, there was no need for anything more complicated. Now, let's fast-forward a few years. The startup became hugely successful. Millions of customers started visiting the website every day. Orders increased dramatically. The development team expanded from a few developers to several engineering teams.

Competition in the market also became much stronger. Suddenly, the architecture that once worked perfectly started becoming a bottleneck. Let's understand why. The first challenge was complexity. Over the years, thousands of features had been added. Several developers had left the company. New developers joined without fully understanding the existing code base. Eventually, no single engineer understood the entire application anymore. Another major issue was tight coupling.

Since all the modules lived inside the same application, changing one module could unexpectedly impact another. Because of this, every small change required extensive regression testing. Even a tiny enhancement could take weeks before reaching production. Deployment became another major pain point. Imagine making a small bug fix in the invoice module. Even though only one module changed, the entire application had to be built and redeployed. That's a lot of unnecessary effort.

The worst scenario is if one module became unstable, it could potentially affect the entire application. Technology evolution also became difficult. Suppose one team wanted to adopt new framework or use a different database, that was not easy because every module depend on the same application and the same technology stack. Finally, team organization became challenging. Since everything was tightly coupled, creating independent agile scrum teams became difficult.

Multiple teams constantly depend on each other, slowing down development and releases. At this point, the leadership realized that the architecture itself had become a business problem. To solve these challenges, the company decided to migrate from a monolithic architecture to microservices. The management allots budgets for the migration and formed dedicated engineering teams to redesign the system. Now, let's see what the new architecture looks like.

On the client side, the company modernized its applications as well. The website is now built using modern front-end frameworks like Angular or React, while the mobile application continue consuming the same backend APIs. Instead of exposing individual services directly, all clients request first to pass through an API gateway. The gateway acts as a single entry point into the system. Behind the gateway, the monolithic application has been divided independent microservices such as identity service, catalog service, order service, invoice, sales, and marketing service.

Each service owns a specific business capability. Even more importantly, each service has its own database. This gives every team the freedom to choose the most appropriate storage technology. For example, catalog may use a relational database, orders may use a NoSQL database to handle massive amounts of transactional data. Marketing may use Redis for high speed caching. Every service choose the technology that best fits its own business requirements.

This is one of the biggest strengths of microservices. The architecture also introduces asynchronous communication. Instead of every service calling another service synchronously, the system uses an event burst such as Kafka or RabbitMQ. For example, when a customer successfully logs in, an event can trigger OTP verification. Similarly, when an order is placed, another event can send an email or SMS confirmation. These operations happen asynchronously, making the overall system faster, more scalable, and more resilient.

We will build similar solutions later in this course, so don't worry if some of these concepts are new right now. Coming back to our discussion, now with this setup, since business capabilities are now isolated into its own microservice, the organization can also create independent development teams. This dramatically improves delivery speed as well. Now, here is the most important takeaway from this lecture. Notice that all these benefits are possible only because the services were divided with the right boundaries.

Imagine if the company had created 50 tiny microservices instead of six well-designed ones, the operational overhead would become enormous, more deployments, more networking, more monitoring, more configuration, more infrastructure. Instead of solving problems, the architecture would introduce new ones. That's why right-sizing is not just important while building a new microservice system. It is equally important when migrating an existing monolithic application.

Choosing the correct service boundaries determines whether your migration becomes a success or an operational nightmare. I hope you are clear. Thank you. And I will see you in the next lecture.
