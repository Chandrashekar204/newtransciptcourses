# 5.3 — What is Encryption, Decryption & why it is not suitable for passwords management

> Section 5: Password Management with PasswordEncoders

Instructor: Most of developers, they assume encryption is the right option for the passwords management. If you're under the same assumption, you are wrong, encryption is not the right option. Let's try to understand why encryption is not the right option for the passwords management. What is encryption? Encryption is a process of transforming data in such a way that guarantees confidentiality. How this confidentiality is going to be assured? Whenever someone is trying to encrypt a plain text value, they're going to use a secret along with the encryption algorithm.

In cryptographic terminology, we call these secret as key. Once the encryption is completed, it can only be reversed by using the same algorithm, and the same secret key. As long as someone take care of securing their secret key and make sure that no unauthorized person can get this key, then we can assume that encryption is a safety process. But still, this is not a recommended approach for passwords management because some person has to generate the secret key, as some application has to generate the secret key very first time during the encryption process.

If the person or if the application, which is trying to generate the secret key, if they lose the secret key, then there is no security or confidentiality in the encryption process. Let's try to understand more details about encryption. Like you can see inside this visual diagram, whenever we have a plain text password, we can apply the encryption along with the secret key, and with that we are going to get an encrypted text. So this encrypted text, in other words, we can also call it as cipher text.

So this encrypted or cipher text can only be decrypted to the plain text using the same secret key. Without that same secret key decryption is not possible. So based upon how these key is being maintained inside the encryption and decryption process, the encryption is categorized into two types. The very first type of encryption is symmetric, and the other type is asymmetric encryption. We know inside the encryption, there is going to be an algorithm along with the secret key.

There are multiple encryption algorithms available inside the industry. So whatever algorithm you are trying to use as part of the encryption, the same algorithm has to be used during that decryption process as well. Now, coming to the key, the key can be managed in two different ways, one is symmetric, and the other one is asymmetric. So let's try to understand what are these two types of encryptions. In the very first type of encryption, which is symmetric encryption, we are going to use the same secret key during the encryption and decryption process.

So you can see here, I have the plain text to value, and to this I'm going to apply some encryption algorithm along with the secret key. With that, I'm going to get a cipher text as an output. Now, if I want to decrypt the cipher text to the plain text value, I need to use the same encryption algorithm. At the same time, I'm also going to use the same secret key. Since we are using the same secret key for the encryption and decryption, this type of encryption, we call them as symmetric encryption.

There is a drawback with the symmetric encryption, though it is trying to provide the confidentiality, if someone lose the secret key to unauthorized persons, then they should be able to do both encryption and decryption. That's why in this scenario, the strength of your encryption depends upon how strongly you are protecting your secret key. Think of a scenario, there is an application, and it want to communicate with various third party applications.

Like there is an application with one, two, three, and four. Since this application A want to communicate with the help of symmetric encryption with all the other third party applications, what it is going to do is it's going to communicate with all these third parties saying that, "Let's try to use a secret key for the encryption and decryption process." Let's assume the secret key value is one, two, three. So the same is distributed for all the third party apps, and the same also being maintained inside the application as well.

Though this application A make sure that this key is well secured, we can't guarantee if the other third party applications, if they have stored and using the secret key for good purposes. If there is a scenario where one of the third party application loses the secret key, there is a very good chance that entire encryption process may get compromised. That's why symmetric encryption is only used in the scenarios where you are trying to encrypt the data in rest or data at rest.

So what is data at rest? Let's take the example of AWS S3 buckets. So inside AWS S3 buckets, we can store any amount of data, it can be logs, or it can be images, videos. You can store any kind of data inside these S3 buckets. AWS, it is going to give an option to their customers if they want to encrypt that data at rest, which is being stored inside the S3 buckets. If the organizations enroll for the encryption, then in this scenario, what AWS is going to do behind the scenes is whenever a new data is being stored into the S3 buckets, it is going to encrypt the data with the secret key, which is known only to the AWS.

AWS is also going to give you an option if you want to provide your own secret key. With that, even if someone get handhold onto the data, which is present inside the S3 buckets, it is going to be useless for them because the data is encrypted and they can't get the secret key either from the AWS or either from the organization. And whenever the organization is trying to read the data from these S3 buckets, AWS behind the scenes, it is going to decrypt the data using the secret key and send the data in a plain format to the organization who owns the data.

So please, make sure you are using the symmetric encryption only in the scenarios of data in rest or data at rest. And, to some extent, you can also use the symmetric encryption if there is only a single application use involved. Don't try to use a symmetric encryption if there are multiple parties involved during the encryption and decryption process. Even if one of the third party application is compromised, then your encryption is going to be useless.

I hope you're clear about what is symmetric encryption. Let's go to the asymmetric encryption. Inside asymmetric encryption, we are going to have two different keys. The very first one is public key, the other one is private key. Whenever someone want to initiate the encryption process, what they are going to do is the owner who is trying to initiate the whole encryption process, they are going to generate two types of keys. The very first one is public key, and the second one is private key.

The owner, they will keep the private key with themself, and they will distribute the public key to any number of third party applications. So whoever has this public key, they will be able to perform only the encryption. So once this encryption is completed, the cipher text is going to be received by the owner who initiated all this encryption process. So the owner during the decryption, they have to use the private key to decrypt the data to plain text.

They can't use a public key for the decryption process. That means anyone can generate the encrypted data with the public key, but the decryption process can be done only by the owner who owns the private key. So this is one style of encryption. Since there are two different types of keys are being used here, we call this approach as asymmetric encryption. This asymmetric encryption is ideal for encrypting the data in transit. Let's try to understand what do I mean by data in transit.

Think of a scenario, there is an application A, and application B. This application A, it want to fetch some data from the application B, it want to read data, but the application A want to read the data only in the encrypted format because application A is very scared that someone may steal the data in between the network. So that's why in this scenario, what application A is going to do is it is going to generate a public key and private key. And this public key, it is going to send to the application B to use it during the encryption process.

So using the public key provided by the application A, the application B, it is going to perform the encryption. Once the encryption is completed, encrypted data will be sent back to the application A. So now think of a scenario, someone in the middle, they hack the data. For them, this encrypted data is not going to make any sense because they don't have the private key to decrypt the data. So who can decrypt this data? It can be only done by application A because it holds the private key.

So this way, both application A and B, they communicated with each other with the help of asymmetric encryption. With all the discussion that we have done so far, you might be under the assumption that "Why can't we use encryption for passwords management? Our application can make sure that no one is stealing the secret key," that can be your assumption, but in reality, it is not going to work that way. You may have people inside your organization only who is looking to steal your secret key.

That's why though these encryption option is providing confidentiality option, it is not providing the integrity option. You can't guarantee that no one can steal you a secret keys or private keys. If someone steals your keys, then all the encrypted data can be easily decrypted by them. That's why we should also not consider the encryption process for the password management. I hope you're clear about the encryption. In the next lecture, let's see the small demo of encryption.
