> Section 9: Implementing Authorization using Authorities,Roles

Instructor: So far, we implemented authorization with the help of authorities. Apart from authorities, Spring Security also allow us to enforce authorization with the help of ROLES concept. There is a very minute difference between AUTHORITY and ROLE. So let's try to understand this difference between them. Once we discuss the differences between them, you will get the clarity under which scenarios you need to select either AUTHORITY or ROLE. When now we are using AUTHORITY inside Spring Security framework, it is going to represent that we are trying to enforce authorization with the help of individual privilege or an individual action.

For example, the authorities that we have choose, like VIEWACCOUNT, VIEWCARDS, so they represent a specific action or a specific invocation that an end user can do inside a system. Whereas the roles inside Spring Security, they are going to represent a group of privileges or actions. Let's take an example to understand this better. Think like inside your application, you have various actions, like VIEWACCOUNT, VIEWCARDS. Similarly, there might be other actions, like UpdateAccount, UpdateCard.

Similarly, there are many other update related actions. You may also have delete-related actions, like DELETEACCOUNT, DELETECARD. What we can do is instead of configuring these end number of actions with the help of authorities inside Spring Security configurations, we can group certain actions into your role. Maybe what I can do all view related actions or authorities, I can tag them to your role user. Similarly, update related actions, I can tag to a role, manager, and anything that comes under the delete, I can tag to your ROLE admin.

If needed, under admin, I can also tag the update and View Authorities as well. Similarly, under manager, I can tag, update and review related authorities as well. So the grouping of the authorities into your role is going to be driven by your business requirements. So someone from business team or your product owner or your business analyst, they're going to give you the requirements that so and so actions or so and so buttons can be clicked by so-and-so user only.

So once you receive these business requirements, as a developer, you need to do the brainstorming with the other developers and other teams, and accordingly, you need to create the roles by grouping the privileges and actions. Here, you may have a question, which is, what is the advantage that I'm getting if I group my roles using authorities? It's a great question. Let's try to understand the same. Whenever you are grouping your authorities using ROLE, the Spring Security related configuration that you have to do will be minimal.

Usually, inside real projects, there'll be thousands of actions that an end user perform inside an application. So configuring all these thousands of authorities or actions using Spring Security configurations is going to be a cumbersome and tedious process. So to overcome this challenge, we can group the authorities or the privileges or actions into your ROLE. And with that, the number of configurations that you have to do on the Spring Security side, they're going to be minimum.

One more difference between AUTHORITY and ROLE is whenever you are using AUTHORITY, you are going to restrict the access in a fine-grained manner. So what is the meaning of fine-grained manner? Fine-grained manner means you are going very deep while enforcing the authorization. Whereas whenever we are using ROLE, we are going to restrict the access in a course-grained manner. Course-grained means we are going to restrict the access on a high level with the help of roles information.
